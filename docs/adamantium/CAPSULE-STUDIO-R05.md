# Adamantium-node Capsule Studio R05 — signed durable review inbox

**Status: isolated reference implementation, not an installed Core service.**

This PR is stacked on R04 (#30), R03 (#26), R02 (#25), R01 (#23).
It does not alter any running Node-RED flow, VM121/VM122, production Core policy, MAS permissions, WireGuard routes or any real language executor.

## Why R05 exists

R03 had an in-memory preview CAS; R04 had an Ed25519-signed client with a completely mocked Core. R05 adds a real **persistent single-writer intake/review queue**, with both the server-side policy callbacks and a loopback-only HTTP adapter. The offer and receipt are cryptographically signed, but the inbox does not have native Graph IR approval authority and **cannot promote, activate, deploy or execute graphs**.

## Trust boundaries

A caller MUST supply all five trust/context inputs; no default permissive path exists:

1. A preprovisioned Ed25519 signer *private key* held by a trusted Core integration. R05 does **not** generate or bootstrap production identities.
2. An authenticated, operator-pinned logical Core node ID and verified policy digest. Writes never fail over to read-only standbys.
3. authenticate(context) — independently authenticates the transport principal.
4. authorize({principalId,graphId,nodeId,policySha256,action}) — independently verifies scoped policy for the exact proposal contract at BOTH offer creation and mutation. A change in policy during asynchronous native validation is rechecked before committing the receipt.
5. nativeValidate({graphId,proposal,expectedRevision,principalId}) — separately provided Core native G0 schema/compiler validator; accepted only with an explicit {accepted:boolean, graphsSha256} bound to the proposed graph documents. Test doubles are **not** actual native validation.

isPrimary() is also mandatory at preflight and before committing. The R04 client and R05 inbox share the exact action/offer/receipt envelope; action IDs are generated by the responder, signed, and scoped to one offer and principal. Offers expire after 60 seconds. Expired offers can be pruned; old idempotency records persist.

The client signs **neither** the request nor a grant: the authorized transport supplies independently verified principal identity. A signed Core receipt means only *accepted for independent review* or *rejected*, not deployed or approved.

## Durable single-writer properties

- The storage directory is an explicit absolute operator-provided path, mode 0700 on creation. There are no fixed hosts or paths in source.
- A .writer.lock is created with O_EXCL and held for the process lifetime. Another writer or a stale crash lock blocks startup; there is no unsafe automatic lock stealing.
- Each mutation prepares a fresh JSON state, verifies it, writes a restricted temporary file, fsyncs, atomically renames it to inbox.json and fsyncs the parent directory where supported. Windows directory fsync limitations mean weaker crash guarantees on that platform; a production-grade store requires a native transactional database.
- Every snapshot is signed with the existing Ed25519 Core key and verified at startup. A hash-chained audit is also verified. These checks detect accidental or unauthorized state edits *without the signing key*. They do not protect against a compromised signer and **do not prove freshness against restoring an older valid signed snapshot**. To prevent rollback attacks, an independent monotonic witness is required.
- Submitted proposals are stored source-free; Graph IR documents and a boundary sidecar carry pinned definition handles but **no language source**, credentials, grants or runnable code.
- The queue is bounded (512 pending, 512 signed offers, 10000 idempotency records, 100000 audit entries, 24 MB state). Saturation fails closed. No automatic destructive garbage collection.
- A requestId is recorded under a JSON-tuple key (principalId,requestId), avoiding ambiguous dot-concatenation collisions; the request and payload hash must match exactly on retry. Successful idempotent retries return the **same signed receipt**, with no second nativeValidation call.
- Every API write is serialized within this one process. After close(), writes are rejected rather than proceeding without the exclusive lock.

The server does **not** increment the authoritative Graph Manager head when accepting review requests; the baseline and CAS head are unchanged. Real compare-and-swap activation and durable review decisions are separate future transactions.

## Optional loopback-only HTTP harness

createCapsuleInboxHttpHarness() requires explicit authenticateHttp(req) and an opened DurableCapsuleProposalInbox. It binds **only 127.0.0.1** and cannot accept a custom external host. It exposes:
- GET /healthz — liveness only, flags authoritative:false, execution:false
- POST /api/proposals/preflight — JSON typed signed offer, authenticated
- POST /api/proposals/invoke — JSON typed candidate, authenticated, signed receipt

No flow execution/admin routes, plugins, CORS wildcard, static files or reverse-proxy ingress. Request body limit 2MB, server timeouts, no debug leaks. Test credentials are generated ephemerally, not embedded in production code.

This harness is for isolated integration testing. To expose a real Core capability, first discover its signed, permission-filtered MAS graph, implement separate Core authentication and G0 native validation, and prove an authorized HTTPS ingress. Never point an unreviewed public proxy to this loopback harness.

## Verification

Run on a disposable checkout (Node.js 22 or 24):

~~~sh
node --test test/adamantium/capsule-*.test.mjs
~~~

Tests include signer verification, persistence across process close/open, immutable monotonic review head, cross-principal authorization checks, expired/used/replayed offers, concurrency, tamper detection, refusing second writer, refusal after close, invalid/missing baselines, and a real loopback HTTP request/receipt round trip. All older graph/Node-RED sidebar tests remain in the same suite.

**Not demonstrated:** live Core MAS authority, actual native G0 code, multi-process distributed locking, permanent review decisions, side-effect-free signer compromise recovery, production roll-forward, real hot-swap, or execution of microprograms.
