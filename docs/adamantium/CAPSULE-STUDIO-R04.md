# Adamantium-node R04 — signed Graph Manager proposal bridge

**Status: standalone source-only contract and test harness. Not deployed.**
Stacked on R03, R02 and R01 draft PRs. The native Mechanicus/Core Graph Manager proposal route has **not** been verified or authorized as a live capability. This implementation must not be interpreted as a working production link.

## Goal

Move beyond the local-only Capsule Studio CAS simulation without allowing the browser editor to invent a Core endpoint or presume execution rights. A transport-neutral Node.js contract accepts an already authenticated capability session supplied by a separate MAS client and performs two narrowly scoped interactions: a signed preflight for exactly one graph, followed by exactly one proposal submission.

The client **cannot** edit Node-RED /flows, modify a running graph, activate a runtime, install a plugin, create a new MAS key, provision a WireGuard peer, or bypass a Core policy. No URLs or credentials are embedded.

## Exact responsibilities

New module: adamantium/capsule-signed-proposal-bridge.mjs

1. Constructor pins a concrete Ed25519 SPKI public key **and** its exact SHA-256 SPKI fingerprint, a logical Core node ID, Graph IR root graph ID and expected policy digest. A supplied transport must implement preflight and invoke (not inferred from Node-RED UI state).
2. Preflight requires status=reachable, mode=primary and canInvoke=true for the exact pinned node. Read-only standby, offline and unknown capabilities fail closed, with no mutation fallback.
3. The preflight payload is an Ed25519 signed, domain-separated, strict JSON offer. It includes nodeId, graphId, policySha256, issue/expiry bounds, unique offerId, authoritative current graph revision and head SHA-256, plus the exact contract and *dynamic* action ID. The client does not invent the action ID.
4. A candidate generated by the inert R03 Graph IR projector must have the exact same root graph and a revision of current+1. Its source-free JSON is SHA-256 bound to a requestId, offerId, expectedRevision and expectedHeadSha256. **One** transport.invoke call is made. No automatic retry after timeout or uncertain server outcome; independent authenticated readback is required.
5. The returned signed receipt must match the proposal hash, requestId, offer, Graph Manager identity, policy digest, revision and previous head. Only accepted-for-review or rejected statuses are recognized. A verified receipt says **only** that this pinned logical node signed the response, not that Core policy authorized promotion.
6. The returned public result *always* states graphApproved=false, runtimeActivated=false, source=pinned-node-identity-only. The actual Core must still perform scoped authentication, native Universal Graph IR schema/compiler validation, persistent CAS, audit logging and MAS policy.

Both signatures use Ed25519 over a domain-separated, sorted-key canonical JSON representation. This is a reference protocol, not an existing server endpoint; implement and version the server-side counterpart only after identifying its real capabilities through the live permission-filtered graph.

## Security model

- A signed offer is **not** a bearer token or permission grant. Transport and Core must enforce authorization again at the write side.
- The Ed25519 public key fingerprint and policy digest are caller-pinned; never auto-discover a new key after an identity mismatch. Never copy a private key into client code.
- A source-definition typeRef is an inert identifier. No Python, Rust, C++, Frankenstein or Node.js microprogram code is executed or included in the proposal.
- A strict schema guard in R03 rejects permission/dependency/route ports and edges, and disguised policy nodes. Graph visuals cannot become MAS permission authority.
- No direct URLs, credentials, assumed network addresses, fallback node, retries, remote writes or permission changes are included in the module.

## Example connector contract (pseudocode only)

~~~js
const bridge = new SignedGraphProposalBridge({
  // Transport MUST already hold an authorized, pinned Core session.
  transport: {
    preflight: ({nodeId,graphId,contract}) => approvedCoreCapability.readOffer({nodeId,graphId,contract}),
    invoke: ({nodeId,actionId,payload}) => approvedCoreCapability.invoke({nodeId,actionId,payload})
  },
  nodeId: pin.nodeId,
  graphId: expectedRootGraphId,
  policySha256: pin.policySha256,
  pinnedPublicKeyPem: pin.publicKeyPem,
  pinnedFingerprint: pin.publicFingerprint
});
const receipt = await bridge.submit({requestId: uniqueId, proposal: inertIRProposal});
~~~

The pseudocode approvedCoreCapability is not a real exported object. Discovery must come from the live, permission-filtered MAS graph. No implementer should substitute a guessed HTTP endpoint.

## Tests

- test/adamantium/capsule-signed-proposal-bridge.test.mjs uses disposable Ed25519 keypairs and purely mocked Core capability transport. It tests correct signed offers/receipts and proof of exact action routing; stale policy, wrong node, foreign graph, tampering, unsupported action contracts, expired offers, unauthenticated standby, replayed offer IDs, uncertain delivery, mismatched receipts and source secrecy.
- test/adamantium/capsule-ir-proposal.test.mjs includes regression cases against disguised permission edges and policy-kind impersonation.
- .github/workflows/capsule-studio-r04.yml tests the complete capsule suite on Linux/Windows Node.js 22/24.

**Not proved:** Production Core accepts this contract, signed nonce persisted across restarts, external CAS is durable, lease/witness trust independence, real hot swap, any published language runtime, or cross-server failover.
